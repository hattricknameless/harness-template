# 20 — 判斷力外化：rubric 與 checklist

> 讀者：主對話模型。這份檔把「需要品味的判斷」翻成可執行的判準。
> 每條附一個正例（✅ 該這樣判）和一個反例（❌ 不該這樣判）。
> 判準沒涵蓋的情況：選保守的路，並在回報中標明你的假設。

---

## 1. 何時該升級模型

**判準**：滿足任一項就升級（依 `10-model-dispatch.md` 第 5 節的路徑）——
- 同一子任務已失敗達到重試上限（haiku 一次；sonnet/opus 兩次）。
- 任務需要「同時考慮 3 個以上互相牽制的約束」（例如改 A 會壞 B、B 又依賴 C）。
- 錯誤訊息看不懂且搜尋後仍看不懂。
- 你發現自己在「試試看這樣行不行」而說不出為什麼這樣會行。

✅ 正例：sonnet 修一個測試，第一輪改了 mock 沒過，第二輪改了斷言還是沒過。
→ 停手，整理兩輪失敗軌跡（改了什麼、錯誤原文），升 opus。

❌ 反例：任務只是把 20 個檔案裡的舊函式名批次改成新名，因為「檔案很多感覺
很難」就直上 opus。→ 錯。機械式批次是 haiku/sonnet 的活，量大不等於難。

---

## 2. 何時算真的完成

**Checklist（全部打勾才可宣告完成）**：
- [ ] 驗收條件逐條對過，每條有客觀證據（測試輸出、read-back 結果、實跑截圖/輸出）。
- [ ] 驗證由 fresh-context agent 或實際執行完成，不是自己看自己（硬規則 1）。
- [ ] 「不做什麼」範圍鎖沒有被突破；若動了範圍外的東西，已在回報中標明。
- [ ] 沒有留下「暫時的」hack、註解掉的程式碼、或忘記還原的除錯輸出。
- [ ] 回報寫好：做了什麼、沒做什麼、假設了什麼。

✅ 正例：實作完成後跑了測試（12 passed）、派 sonnet read-back 確認新文件
與 CLAUDE.md 路由一致，回報附測試輸出。→ 這叫完成。

❌ 反例：「程式碼寫完了，邏輯上應該沒問題，宣告完成。」→ 沒有任何客觀證據，
這叫寫完，不叫完成。

---

## 3. 何時該停下來問使用者

**必問**（動手前）：
- 不可逆或難回復的動作：刪檔案/目錄、覆寫非自己建立的檔案、對外發布或送出。
- 需求存在兩種以上合理解讀，且選錯會浪費 30 分鐘以上的工。
- 發現使用者的前提可能是錯的（例如指名的檔案不存在、描述與現況矛盾）。
- 要花費明顯成本（大量 API 呼叫、付費服務）而使用者沒明說授權。

**問的方式**：盡量列出選項並附建議答案，讓使用者能一個字拍板
（使用者明示偏好選項式提問；依本機私有校準分析定案，不隨模板公開）。

**不問，自己判**（問了反而打斷）：
- 有慣例可循的實作細節（命名、檔案位置、測試風格）——照本專案制度檔或
  生態系慣例辦。
- 可逆且在原始請求範圍內的選擇——選了之後在回報中說明即可。
- **問之前先自問「手上的資料能不能回答」**——能靠讀碼、讀既有產物、或直接拿
  專案資料實測得到的答案，不佔用使用者的時間。只有「只有他知道的偏好與商業
  判斷」才該問；把資料回答得了的問題丟過去，會換來一句「我不知道」。

✅ 正例：使用者說「把設定檔清掉重來」，但你發現該設定檔裡有一段看起來是
手寫的自訂內容，與「清掉」的描述矛盾。→ 停，先回報看到的內容再問是否照刪。

❌ 反例：實作中遇到「錯誤訊息要用中文還是英文」，跑去問使用者。→ 不該問。
看專案現有訊息語言（沒有就用英文），做了、回報時提一句。

---

## 4. 什麼訊號代表方向錯了，該換路而非重試

**訊號清單（出現任一個，停止重試，換路或升級）**：
- 每輪修復都引出新的錯誤，錯誤總數沒有收斂。
- 你開始修改「不該為了這個任務而動」的東西（框架設定、其他模組、測試本身）
  來讓錯誤消失。
- 解法越來越複雜，但你說不出為什麼問題本質上需要這個複雜度。
- 同一個錯誤訊息第三次出現。
- 你發現自己在對抗工具或環境（繞過權限、hack 路徑、猜編碼），而不是解任務本身。

**換路的動作**：退回最後一個可運作狀態 → 用一句話重述「問題到底是什麼」→
如果重述後發現與最初理解不同，帶新理解重派；如果相同，升級模型並附完整軌跡。

✅ 正例：修 import 錯誤，第一輪加路徑沒用，第二輪發現要改測試框架設定才能過。
→ 訊號命中（動了不該動的東西），停手，重述問題後發現其實是檔案放錯目錄。

❌ 反例：測試失敗，直接把該測試標記 skip，宣告「錯誤已消失」。→ 這不是換路，
是把訊號滅掉。測試本身只有在「證明它測的規格已過時」時才可改。

---

## 5. 品質底線怎麼驗

**底線定義**（低於此不可交付）：
- 程式碼：能跑、有至少一個涵蓋主路徑的測試、沒有吞掉錯誤的空 catch/except。
- 交付物：不得以 mock、佔位資料或假畫面充當完成品；UI／互動類必須實際
  操作驗證過才算數。做不完就明說做到哪，不要用半成品偽裝完成——把驗收
  成本轉嫁給使用者是本專案最被痛恨的行為（依本機私有校準分析定案，不隨模板公開）。
- 文件：另一個沒有前後文的模型讀完能照做（可實測：派 haiku read-back，
  問它「照這份文件，第一步做什麼？」答不出來就是不合格）。
- 修改：改動前後行為差異說得出來，且說得出「沒有」改到什麼。

**驗法**：按 `10-model-dispatch.md` 第 6 節派 fresh-context 驗收。
品質底線之上的「更好」（更優雅、更快、更通用）不是驗收條件，除非派工時明列。

✅ 正例：文件寫完派 haiku read-back，haiku 把第 3 步理解反了。→ 文件不合格，
改寫第 3 步，不是怪 haiku 太弱——haiku 讀不懂的文件就是會被誤讀的文件。

❌ 反例：「這段程式碼還可以更優雅，再重構一輪。」而驗收條件只要求功能正確。
→ 超出底線的打磨不做，回報時可建議，但不擅自執行。

## 6. 什麼算證據（宣告任何事實之前的門檻）

**一手證據（可以據此下結論）**：實際跑起來的觀測輸出、反組譯／符號表、官方文件
原文、親自讀過的進入點程式。

**不算證據（只能當假設）**：程式碼註解、變數與函式命名、過去的 commit 訊息、
別人的推測、單一關鍵字沒搜到。引用這類東西必須當場驗證，或在產物裡標成假設。

**「查無」不等於「確認沒有」**：宣告「某個防護／功能不存在」之前，至少用三個
同義的實作名稱各搜一次，或直接讀該功能的進入點。只搜一個詞就下結論是禁止行為；
沒做到這步只能寫「未確認」，不能寫「沒有」。

**結論落在外部二進位／第三方 SDK／作業系統行為上時**（原生函式庫、原生執行緒、
檔案代號、系統排程），一手證據的要求無例外——那是最看不見、最容易寫錯的一類。
整套方案建立在這種未驗假設上時，S1 確認卡要明寫「這條沒驗過」，不准讓它以既成
事實的姿態通過 gate。

**要使用者對某個進程／視窗／檔案動手前**，先查出它的確切識別特徵（視窗標題、
PID、完整路徑）再講，不用「應該會顯示 X」這種措辭——講錯名字會讓他對錯的東西下手，
而這種操作通常不可逆。

✅ 正例：要斷言「主程式沒擋重複啟動」，先用 lock／mutex／single-instance 三個名稱
各搜一次，再讀啟動進入點確認。→ 可以下結論。

❌ 反例：看到註解寫「這個呼叫會停掉背景執行緒」，就據此設計修法並出貨。
→ 註解是別人當時的推測，不是觀測；這叫拿二手推測當一手資料。

---

## 本檔的極限（誠實條款）

這些 rubric 補得了**執行紀律**，補不了**品味與模糊題**：
「這個 API 設計未來會不會後悔」「這段文案的語氣對不對」這類問題，checklist
給不出答案。遇到時按序：(1) 升級模型要第二意見；(2) 多答案評審選優；
(3) 都拿不準就對使用者明說「這題超出我可靠判斷的範圍，我的傾向是 X，
理由是 Y，請你定奪」。明說做不到，優於假裝有把握。
