# 10 — 模型調度守則

> 讀者：本專案的主對話模型。**指揮官預設 Opus**（2026-07-06 使用者定案）；
> 規則仍以「Sonnet 也指揮得動」為底線設計，Sonnet 接手時照本檔走即可。
> 此預設只管主對話——派 subagent 照第 3 節指定表，從最便宜檔位起跳。
> 依據：`00-design-baseline.md` 的三大失效模式。
> 派工時直接套 `templates/` 下的模板，本檔負責「派給誰、怎麼管、怎麼收」。

## 0. 本環境實況（2026-07-05 實測，變動時依 30-maintenance 更新本節）

- Agent 工具可用的 `model` 參數：`haiku`、`sonnet`、`opus`、`fable`。
  （`fable` 是否可派取決於方案；派不動時 fallback 到 `opus`。）
- 常用 `subagent_type`：
  - `Explore` — 唯讀搜尋掃檔，不能寫檔。適合大範圍找東西。
  - `Plan` — 唯讀規劃，回實作計畫。
  - `general-purpose` — 全工具，適合實作與多步任務。
  - `claude-code-guide` — 只用於回答 Claude Code / API 本身的問題。
- **effort 參數視派工方式而定**（2026-07-22 修正 2026-07-05 的舊實測）：
  - **Agent 工具（日常派 subagent）**：沒有獨立 effort 參數。只能用兩個手段
    近似——(a) 換模型；(b) 在派工 prompt 裡明寫思考深度要求（例如「動手前先想
    清楚 edge cases 再實作」）。不要在 Agent 工具呼叫裡發明 effort 欄位。
  - **Workflow 工具（多 agent 編排）**：`agent()` 有 `opts.effort`，五級
    `low`／`medium`／`high`／`xhigh`／`max`。要把某關（如 pipeline S5 閱卷）的
    effort 明確開高，走 Workflow 編排時才用得到這個旋鈕。
- 其他可用資源：MCP（Figma / Canva / Notion）、記憶目錄
  （`~/.claude/projects/<本專案>/memory/`）、skills（/code-review、/verify 等）。
- **平台陷阱（Windows／PowerShell 5.1，會直接毀檔或讓工作靜默不跑）**：
  - **改既有檔案一律用 Edit／Write 工具，shell 只拿來跑指令。** 用 shell 做文字
    取代會毀掉非 ASCII 內容（該版 PowerShell 讀寫預設編碼不是 UTF-8），而且取代
    規則可能命中它自己不該動的地方。
  - **要交給 `powershell -File` 執行的腳本一律純 ASCII**（訊息寫英文，中文留到
    回報時再翻）。工具寫出的無 BOM UTF-8 會被以 ANSI 解讀，中文碎掉會吃掉引號與
    大括號，腳本在解析階段就掛——排定的工作等於沒跑，而且不會有人發現。非用中文
    不可時改用 `-Command` 傳字串，並先實跑驗證一次再排程。

## 1. 指揮官不下場

主對話（指揮官）的 context 是全 session 共用預算，只進結論、決策、與使用者的對話。

**一律派 subagent 的操作**：
- 讀取超過 2 個檔案或任何單檔超過 ~400 行的內容蒐集
- 目錄掃描、關鍵字全域搜尋（派 `Explore`）
- 查網頁、讀文件、外部研究
- 批次改檔（同一種修改套用到 3 個以上檔案）
- 跑會產生大量輸出的指令（完整測試套件、build log）

**指揮官可以自己做的**：
- 讀 1–2 個已知路徑的小檔（<~400 行）
- 單點編輯（1–2 個檔案的小改動）
- 跑輸出可控的單一指令
- 與使用者澄清需求

判斷式：「這個操作會把多少原始資料拉進主對話？」超過一頁就派出去。

## 2. 派工三件套（缺一不派）

每個派工 prompt 必含：
1. **目標與動機** — 要什麼、為什麼要（動機讓 subagent 在邊界情況能自己判斷）。
2. **驗收條件** — 可客觀檢查的完成定義，含「不做什麼」的範圍鎖。
3. **回報格式** — 回報的結構、長度上限、落檔規則。

模板在 `templates/`，照填即可。三件套寫不出來 = 你自己還沒想清楚，先想清楚再派。

## 3. 模型指定表

| 任務 | model | subagent_type |
|---|---|---|
| 機械式搜尋、格式轉換、照既有模式批次套用 | `haiku` | Explore / general-purpose |
| 一般搜尋、一般實作、寫測試、文件整理 | `sonnet` | Explore / general-purpose |
| 跨檔架構設計、難 bug、需求歧義大的規劃 | `opus` | Plan / general-purpose |
| 前面都失敗的僵局、高風險判斷的第二意見 | `fable`（派不動則 `opus`） | general-purpose |

預設從表列的最便宜檔位起跳；拿不準時，寧可從 `sonnet` 起，不要直上 `opus`。

**派工前先對過該 agent 型的工具權限與產物要求**：唯讀型（`Explore`、`Plan`）
不能落檔，套一個要求「寫進某某檔」的模板會當場卡死，只能由指揮官轉存（轉存要處理
跳脫字元，有失真風險）。要 agent 自行落檔就派 `general-purpose`，否則模板改成
「回報全文、指揮官落檔」。

## 4. 回報合約

寫進每個派工 prompt 的固定條款：
- 只回**結論**與**證據指標**（`檔案:行號` 格式），不貼大段原文。
- 超過 ~30 行的產物寫到指定路徑（研究報告與要留存的結果放 `docs/notes/`，
  目錄不存在就建立；用完即丟的臨時物放 scratchpad），回報只給路徑 + 3 行摘要。
- 明確回報「做了什麼、沒做什麼、卡在哪」三段，禁止只報成功面。

subagent 違約（貼了大量原文回來）時：這次先用，但下次派工把長度上限寫得更狠
（例如「回報全文不得超過 20 行」）。

**收工核對時，「沒做什麼／假設了什麼」要當風險清單逐條讀，不是當免責聲明讀過去**：
每一條問一次「這條在真實負載、真實環境下會發生什麼」，有疑慮就地開驗證或列成
追蹤項再收。被略過的一句「未優化」「先假設如此」，出貨後就是使用者踩到的那個問題。

## 5. 升降級路徑

- **haiku 錯一次** → 直接升 `sonnet`，不給第二次。
- **sonnet / opus 同一子任務連錯兩次** → 升一級，且必須附**完整失敗軌跡**
  （每輪做了什麼、錯在哪、錯誤訊息原文），不是只把原始任務再丟一次。
- **解出模式後降級**：一旦某類問題被高階模型解出「可複製的做法」，把做法寫成
  明確步驟，降回 `haiku`/`sonnet` 批次套用到其餘案例。
- **fable 也失敗兩輪**：已無更高檔位，只能換路（重新定義問題）或帶完整
  軌跡回報使用者請他定奪，不再重試。
- **同一件事最多重試兩輪**（含主對話自己動手的情況）。第三輪前必須改變其中
  之一：模型、做法、或問題定義。三者都不變的重試是禁止行為。

## 6. 驗證不自驗

寫東西的人不驗收自己的東西。驗收方式按產物類型：

| 產物 | 驗收方式 |
|---|---|
| 檔案（文件、設定） | 派 fresh-context subagent read-back：讀檔並回答「這份檔在說什麼、有無內部矛盾、有無指到不存在的路徑」 |
| 程式碼 | 跑測試或實跑（可用 /verify skill）；沒有測試就先寫最小測試再驗 |
| 高風險判斷（架構選型、刪東西、對外動作） | 第二意見：派另一個 fresh-context agent 獨立評估；或多答案評審——派 2–3 個 agent 各給方案，再派一個評審 agent 選優並說明理由 |

Fresh-context 的意思：驗收 agent 的 prompt 只給「產物路徑 + 驗收條件」，
**不給**產生過程的推理與草稿，避免繼承盲點。

**pipeline 裡程式碼的「不自驗」升級為三角色分立**（見 `40-pipeline.md` S4／S5）：
出題（設計驗收測試）、實作、閱卷是三個獨立空視窗，出題者不得是實作者、閱卷者不得是
另外兩者。理由——實作者若自己出驗收測試，對需求的誤解會同時寫進程式與測試，測試綠燈
卻蓋掉 bug，等於自驗。模型：出題／閱卷用 opus（閱卷最難、最不該省），實作用 sonnet。
