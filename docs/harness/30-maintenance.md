# 30 — 維護協議：如何安全地更新制度檔與 skills

> 讀者：未來任何想修改 `CLAUDE.md`、`docs/harness/` 或 `.claude/skills/` 的模型。
> 原則：制度檔與 skill 是所有 session 的共用基礎設施，改壞的代價由之後
> 每個 session 承擔。

## 1. 權限分級

**可自行修改（改完在回報中告知使用者即可）**：
- `10-model-dispatch.md` 第 0 節「本環境實況」——型號、工具、skill 清單過時就更新。
- 各檔的「建制時的假設」段落——假設被實況推翻時修正。
- `templates/` 新增模板、或在既有模板加欄位。
- 各檔追加「教訓」條目（格式見第 3 節）；`.claude/skills/` 追加教訓／
  gotcha 條目（演化協議見第 5 節）。

**動之前必須先問使用者**：
- 修改或刪除 `CLAUDE.md` 的硬規則。
- 刪除任何制度檔或 skill、或大幅改寫（超過該檔三分之一）。
- 修改 `00-design-baseline.md` 的三大失效模式本身（追加預防手段不用問）。
- 放寬任何上限（重試次數、回報行數、驗證要求）。收緊不用問。

## 2. 版本保護程序（硬規則，改任何制度檔前執行）

> 2026-07-07 使用者定案：專案已 git 化，版本保護全面改用 git；
> 原 `_backup/` 副本機制廢除、舊備份檔已移除。

1. 動手前確認要改的檔案沒有未 commit 的改動（有就先 commit），
   確保 git 裡留有改動前的版本可回復。
2. 改完後，用 `20-judgment.md` 第 5 節的文件底線驗法驗收
   （派 fresh-context read-back）。
3. 若修改影響路由或檔名，同步更新 `CLAUDE.md` 的目錄結構與路由表。
4. 收尾時把制度檔改動 commit（`docs:`／`chore:` 開頭，見 `50-versioning.md`）。

## 3. 教訓寫回（每次踩坑後）

**寫到哪**：
- 派工/模型選擇踩的坑 → `10-model-dispatch.md` 末尾「教訓」節。
- 判斷失誤（該問沒問、該停沒停）→ `20-judgment.md` 對應小節追加正/反例。
- 模板欄位不夠用 → 直接改該模板。
- 環境陷阱（工具行為、平台怪癖）→ `CLAUDE.md` 若會出大事，否則
  `10-model-dispatch.md` 第 0 節。

**格式（固定三行，控制膨脹）**：
```
- [YYYY-MM-DD] 坑：＜一句話，發生了什麼＞
  因：＜一句話，為什麼會發生＞
  改：＜一句話，之後怎麼做／已改了哪條規則＞
```

寫教訓可直接追加（不算修改既有內容）；改既有規則才走第 2 節程序。

## 4. 精簡協議（防止制度檔長成沒人讀的長文）

**觸發條件（任一達標就精簡）**：
- 單一制度檔超過 250 行。
- 「教訓」條目超過 10 條。
- CLAUDE.md 超過 80 行。

**精簡方法**：
1. 先走第 2 節版本保護程序（確認改動前版本已在 git）。
2. 教訓條目中已經「畢業」的（規則本文已吸收其內容）直接刪除。
3. 重複或互相包含的規則合併，保留較具體的那條。
4. 精簡後 read-back 驗收：問驗收 agent「精簡前後有沒有規則消失或變弱」，
   有就補回。
5. 精簡屬於大幅改寫時（超過三分之一），先問使用者。

## 5. Skill 自我演化協議（有合成，就要有代謝）

> 概念源自使用者在 GameGen Service 的 verify-in-browser skill（用完寫回
> gotcha），本節補上該做法缺的另一半：修剪。只加不減的自我演化 =
> sediment，過期的指南比沒有指南更毒。

**寫回（每次用完 skill）**：執行中遇到 surprise（方法陷阱、覆蓋缺口、
環境怪癖）→ 當場追加條目到該 skill，格式四行內：症狀／因／修法／肇事處
（`檔:行` 或指令）。追加不需先走第 2 節程序。

**標壽命（寫回時就做，事後補很難）**：每條新條目標註日期＋壽命類別——
- `[耐久]`：平台／協定層的事實（如「synthetic event 繞過 hit-testing」）。
- `[環境]`：dev 環境、工具版本的怪癖——環境換掉就過期。
- `[階段]`：綁定專案當下狀態的事實（帳號、port、feature flag）——
  最快過期，過期後照著做會直接做錯。

**代謝（觸發條件：SKILL.md 超過 150 行、或條目超過 10 條）**：
1. 先走第 2 節版本保護程序（確認改動前版本已在 git）。
2. 逐條檢查：`[階段]`／`[環境]` 條目指涉的東西還存在嗎？不存在就刪。
   已被吸收進本文規則的條目（畢業）也刪。
3. 還有效但非每次都用的 `[耐久]` 條目 → 搬到同目錄的 reference 檔
   （如 `gotchas.md`），SKILL.md 本文留一行指標。本文只留每個分支
   都會用到的步驟。
4. read-back 驗收：「精簡前後有沒有規則消失或變弱？」有就補回。
