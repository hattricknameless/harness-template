# 40 — 開發 Pipeline：需求 → 規格 → 設計 → 拆解 → 實作 → 驗收

> 讀者：主對話模型（指揮官）。**觸發：使用者交辦任何功能或 bug 修復——不分大小、
> 不用打 `/pipeline`，一律自動走本檔。** 功能與 fix 是同一套流程；份量只決定**深度**
> （見 §0 份量分級），**grill 對齊與 S5 驗收永遠都跑**。
> 本檔只管**流程與產物**；派給誰、重試上限、驗證不自驗等底層規則在
> `10-model-dispatch.md` 與 `20-judgment.md`，本檔不重複、衝突時以它們為準。
> 少數情況才用的兩段（難 bug 的診斷支線、定案前的試效果模式）在
> `41-pipeline-branches.md`，何時必讀見本檔末「兩條支線」。

- **產物目錄**：`docs/specs/<YYYYMMDD-slug>/`（spec.md、design.md、tasks.md、
  審查報告）。一個功能一個目錄。
- **人類 gate：S1 確認卡核准永遠必經**；**S2 設計核准是完整深度才有的第二道
  gate，小份量時可併入 S1 確認卡或省略**（見下方份量分級）。最後一道 gate 通過後
  S3–S6 全自動跑完，中途只有命中 `20-judgment.md` §3「必問」條件時才回頭問使用者。
- **份量分級（指揮官自判，開工前一句話宣布歸哪檔，使用者可否決）**：每件事都跑完
  S0–S6，但各階段深度按下表縮放。**只有 S1 確認卡 gate 與 S5 驗收永不省；碰資料／
  資金／live 交易一律至少走到確認卡 gate，不准直接動手。** 拿不準份量往上一檔靠。

  | 面向 | 小修 | 中 | 大 |
  |---|---|---|---|
  | 歸類判準 | 局部、行為明確、可逆、不碰資料/資金/live | 有歧義／動到你在意的既有行為／碰資料/資金/live／不可逆（跨模組但你在旁監督也算這檔） | 整塊系統級模組，且你授權過夜自主跑到可上線 |
  | S1 grill | **0–1 題**（只確認我理解的症狀/需求對不對；零歧義就無可問） | **2–4 題**（要做什麼＋怎麼驗收＋邊界） | **窮盡各面向**（不設上限） |
  | S1 確認卡 | 三格（重現/期望/完成） | 完整版（約一頁） | 完整版 |
  | S2 設計 gate | 併入確認卡或省略 | 完整白話設計摘要 | 設計摘要，高風險再 Design It Twice |
  | S3 拆解 | 常單片 | 數片 | 多片、可平行 |
  | S4 角色分立 | 出題可併入實作（同一 agent 先紅後綠），**但獨立閱卷永不省** | 出題／實作分立（出題 opus、實作 sonnet） | 三者全分立，閱卷可再加第二位獨立 reviewer |
  | S5 驗收 | Spec 軸＋交付前全套一次 | ＋Standards 軸 | 完整矩陣 |
  | 走法 | 自動 pipeline | 自動 pipeline | 自動 pipeline，照本檔完整深度跑（`/epic` 重型模式尚未內建，見末節「待辦」） |
- **三角色分立（不自驗的落實，2026-07-22 使用者定案）**：出題、實作、閱卷是
  三個獨立空視窗。**出題者不得是實作者**（小修例外：出題可併入實作，見上表 S4 列）；
  **閱卷者不得是出題者也不得是實作者**（任何份量都不例外）。理由見
  `10-model-dispatch.md` §6 與 `templates/feature-review.md` 開頭。模型：閱卷最難（要找漏做、假通過這種「不存在的東西」），
  用 opus、最不該省；出題次之（opus）；實作最機械（sonnet）。
- **gate 給使用者看的是白話產物，不是結構化產物本身**（2026-07-19 使用者定案）：
  S1 給確認卡、S2 給白話設計摘要（格式見各節），全中文口語、寫給使用者讀、讀完能拍板。
  spec.md／design.md 是給 agent 讀的內部檔，可保持技術性與英文欄位，絕不要求使用者讀。
- **中斷恢復**：知道需求後、進 S0 之前，先看 `docs/specs/` 有無 tasks.md
  未全部完成的目錄；有就問使用者續跑還是新開，續跑則從 tasks.md 的狀態接續。
- **全程計時（不含等使用者的時間，2026-09-10 定案）**：接到需求的第一件事、每次階段換手、
  以及 S6 收尾，各記一次目前時刻，一行一筆（階段｜時刻｜備註）。
  停下來等使用者回覆的區間記成「等待」，算總時間時扣掉。
  **記在哪**：spec 目錄要到 S1 才定案，所以在那之前的時刻先記在自己的回報裡；
  S1 建 `docs/specs/<YYYYMMDD-slug>/` 時一併建 `timing.md`，
  把先前那幾筆補寫進去，之後每筆都直接寫這個檔。
  S6 回報要附這張表，並指出最久的環節與為什麼久。
- **測試怎麼跑（省掉重複，不省驗收；2026-10-19、10-22 使用者定案）**：開發中只跑這個
  功能的測試，全部測試（全套）只在交付前跑一次。

  | 時機 | 跑什麼 |
  |---|---|
  | 出題者確認紅、實作者確認綠、修小東西、故意改壞程式看會不會紅（反證） | **只跑相關測試**：這片的新測試＋這次改到的模組的既有測試；改數值或資料檔時，用舊數值與資料檔路徑搜得到的測試也算 |
  | 全部片做完、送閱卷之前 | **不跑全套**。閱卷看每片的相關測試紀錄，反證只跑相關測試 |
  | 閱卷與所有修改（含補測試）都做完之後 | **全套一次，含慢測試**，這就是交付前那一次。閱卷沒有要改的，也是在閱卷之後跑這一次 |

  - **會改資料檔的步驟排在全套之前**：產生或重算資料、資料遷移、產生附屬檔這類會改
    資料檔、設定檔或場景的步驟，全部做完才開始跑全套。全套跑完才改資料，那次全套就作廢，要再跑一次。
  - **交付前那次全套紅了**：只改測試（偶發失敗、測試順序造成的）→ 修完只跑相關測試，
    再跑一次全套。改到產品程式 → 再派一次範圍只限這次修改的閱卷（由它做反證），再跑一次全套。
  - **同一份程式不跑第二次全套**：要跑全套前先看測試紀錄。上一次全部通過的全套開始之後，
    原始碼、測試、場景、資料檔都沒被改過，就直接引用那一行紀錄。判斷有沒有改過：紀錄有
    程式指紋（由當時全部檔案內容算出的一串識別碼，內容一變就不同）就比指紋；沒有就看
    檔案修改時間——一次執行分成好幾行紀錄時，取最早那一行的開始時刻來比；期間有刪檔或
    搬檔就不能引用；閱卷者反證後已用版本控制的差異比對確認改回、一模一樣的，修改時間變新
    不算改過。紀錄是測試腳本自動寫的才算數，不算轉述；指揮官照這條，不重跑。
    測試腳本還不會自動寫紀錄的專案，先補上（每跑一次記一行：開始時刻、跑了哪些、
    有沒有排除慢測試、結果）。
  - **交付依據只能是含慢測試的全套**：排除慢測試的全套（例如自己為了查問題手動跑的），紀錄行不能拿來
    當交付前那一次引用。
  - **慢測試另成一組**：單條超過 1 秒的測試要標成「慢測試」分類，並在測試開頭寫明為什麼慢。
    平常不跑（相關測試排除這一組）；改動碰到它在測的東西時，相關測試要包含它；
    交付前那次全套一定跑。測試腳本還不能排除這一組的專案，先補上這個開關。
  - **反證只由閱卷者做**：反證＝故意把產品程式改壞，看該紅的測試會不會紅（不會紅就是
    測試沒測到東西）。出題者、實作者、指揮官不各做一份（例外見下一條）；改壞後只跑相關測試，
    閱卷者不等全套、讀完每片的相關測試紀錄就開始。不管誰做反證，每改壞一處都先看差異比對，
    確認真的改到了，才相信接下來的紅或不紅；全部改回後再用差異比對確認跟反證前一模一樣。
    閱卷者這側的做法見 `templates/feature-review.md`。
  - **閱卷後補的東西怎麼驗（2026-10-22 使用者定案）**：閱卷者把測試沒抓到的每一處寫成
    「沒抓到的改壞清單」（哪個檔、改成什麼——寫到別人照做得出來、哪類測試應該紅卻沒紅）。
    **只補測試、沒改產品程式**時，不另派閱卷：指揮官照這份清單逐條改壞、只跑相關測試，
    確認補的測試都變紅，再用差異比對確認改回。補測試的人多寫了清單以外的測試，要在回報裡
    替每一條附一處「改哪裡、改成什麼它就會紅」，指揮官一樣照做驗紅。這是照清單實際跑出來的
    結果，補測試的人不是指揮官，所以不算自己驗自己。**有改到產品程式**時，照舊再派一次
    範圍只限修改部分的閱卷，由它做反證。
  - 底線不變：交付前一定有一次全套全部通過（含慢測試），加上獨立閱卷。

## S0 摸底

派 Explore 掃：相關模組、既有慣例（測試風格、目錄結構）、可複用的 seam。
若存在 `CONTEXT.md`（詞彙表）與 `docs/adr/`，指揮官自己讀——之後所有階段的
用詞照 glossary、決策尊重 ADR。`docs/ROADMAP.md`（使用者說過之後確定要做的功能）
存在也自己讀，S1 要拿它對照（見 §S1「以後確定要做的先想好」）。

**固定掃兩側，缺一不可**：
- **資料來源側**——輸入從哪來、會經過哪些既有模組。
- **產出物形狀側**——專案裡有沒有已經長得很像的成品、它已經做到幾成？
  只掃來源側會把「補兩個切換」誤判成「另做一套」。

**完成判準**：能說出「這個需求會碰到哪些既有東西」「有沒有可沿用的既有成品、
它還缺什麼」，或確認是綠地專案。
（綠地且需求是從零開始 → S0 可跳過。）

## S1 規格（grill → spec.md）

指揮官與使用者對齊需求，規則：

1. **一次只問一個問題，每題必附建議答案**。一次拋一串問題會讓人無所適從。
2. **能靠讀碼回答的不問使用者**（派 Explore 查）。
3. 問到雙方對「要做什麼、怎麼驗收」沒有歧義為止；沒有歧義的需求不硬問。
4. 使用者若說「全自動／不要問我」：改為批次列出所有決策點＋你採用的建議答案，
   全部寫進 spec 的 Assumptions 段，直接進 gate。
5. **grill 題數照 §0 份量分級表**。grill 這關永遠跑——不問不代表跳過，確認卡本身
   就是 grill 的產出，仍要使用者點頭。
6. **以後確定要做的先想好**（避免下一個功能回頭拆改這次的東西）：
   - 先讀 `docs/ROADMAP.md`（S0 讀過就不重讀；S0 跳過也要讀）。
   - **中、大份量必問一題**（算一題，在題數內）：「這一塊之後還確定要加什麼？」建議
     答案由指揮官主動想——ROADMAP 裡碰到同一塊的，加上這類功能通常接下來會要的延伸
     （例：做了單人存檔，通常接著要多存檔欄位、雲端同步），每條附一句為什麼通常會要；
     列成清單，請使用者一次逐條標「確定會做／可能／不會」，拿不準就標「可能」。
     全自動模式下指揮官不能替使用者標「確定」：只有 ROADMAP 裡已有的算確定，其他
     猜測一律當「可能」。
   - **小修**不另問，但仍對照 ROADMAP；這次碰到其中某條、或要先頂著（見下），
     在三格確認卡後面加一行：「以後要接上的：…」或「先頂著、要你決定：到時要拆…」。
   - **確定會做的** → 這次的介面、資料格式、擴充位置要設計成到時候能直接接上
     （理想是只加新東西、不改這次的）；**只預留形狀，不寫那個功能本身**。
   - **可能／不會的** → 不預留任何東西；兩種寫法花的工一樣時，選不擋它路的那種，
     要多花工就不管。
   - **禁止明知會拆的快速寫法**：某個功能確定會做，這次卻用一個到時一定要拆掉重寫
     的做法先頂著（只為了現在快），一律不准。真的要先頂著（例如等外部條件），
     列進確認卡「我假設」並標「這個要你決定」，寫明到時要拆什麼。
   - 使用者新說出的「確定會做」→ gate 通過後追加進 `docs/ROADMAP.md`（沒有就建；
     一條一行：功能＋一句話＋哪天說的）。使用者改口不做 → 刪掉那條。

**spec.md 欄位**（依序）：
- `## Problem` — 使用者視角的問題。
- `## Solution` — 使用者視角的解法。
- `## User Stories` — 編號列表，格式固定 `As a <角色>, I want <功能>, so that <效益>`，
  盡量窮盡各面向。
- `## Implementation Decisions` — 模組、介面、schema、API 合約等決策。
  **禁止寫具體檔案路徑與程式碼片段**（會過時）；例外：prototype 產出的
  狀態機／reducer／type shape 片段可內嵌並註明來源。
- `## Testing Decisions` — **seam（測試邊界）清單**：測試只打在這裡。
  越少越好，理想是 1 個；優先複用既有 seam。此清單是**內部決策，不強求
  使用者核准**（他不必懂 seam）；由 S2 的 read-back 把關其合理性。
- `## Out of Scope` — 明列不做什麼。
- `## Future-Proofing` — S1 第 6 條的結果，每條：確定會做的未來功能｜這次預留
  什麼（介面、資料欄位、擴充位置）｜這次刻意不做什麼。沒有就寫 None。
- `## Assumptions` — 未經使用者確認、由你代答的決策（全自動模式必填）。

**寫「比對通過才准動作」的閘門時**（健全性檢查、對帳門檻、拒絕寫入條件），
逐條**自問**（不是拿去問使用者）「**這道閘的比較樣本裡，有沒有包含正是這次要修
的異常？**」有就在 spec 明寫排除規則——防禦條件與修復目標指向同一份資料時，防禦會
反過來擋掉修復，而且擋在最需要它成功的那一天。這種規則要在 S3 配一條測試，並由閱卷者
反證（把排除邏輯拿掉必須變紅），否則測試會跟著實作一起錯。

**gate 產物：白話確認卡**——spec.md 寫完後，指揮官據它生一張給使用者的確認卡，
在對話裡呈現（不是叫使用者讀 spec.md）。確認卡全中文口語、約一頁（小修縮成三格，
見 §0 份量表），格式如下：
- 一句話標題：這次要做什麼。
- **問題／現況**：使用者視角，為什麼要做、現在卡在哪（1–2 句）。
- **要做**：條列，講「系統會有什麼行為」，不講改哪個檔、不用內部術語。
- **打算怎麼做**：大方向白話——採哪個做法、為什麼選它、放棄了哪個替代方案
  （講策略與取捨，仍不講檔案／函式／程式碼）。**必須明寫「沿用既有的 X、
  缺的只有 Y」或「為什麼不能沿用 X」**，不准跳過這個比較就端出新造方案。
- **不做**：這次明確不碰的（白話 out of scope）。
- **以後要接上的**：你說之後確定會做的功能，這次先留好哪裡、讓那時不用回頭改；
  每條附一句這次多花的代價（沒有就寫「無」）。
- **會影響到**：會動到哪些使用者看得到的現有行為、有什麼風險（沒有就寫「無」）。
- **完成長怎樣**：可觀察的驗收條件，不准寫「運作正常」。
- **我假設**：代答的決策，每條附「不對跟我說」；其中真正該由使用者拍板的，
  另標「這個要你決定」。
結尾一句請使用者回「可以」或指出哪裡不對。禁止在確認卡裡出現英文欄位標題、
函式名、程式碼、`檔案:行號`。份量校準：寧可在「打算怎麼做／會影響到」多給
一兩句取捨與風險，也不要砍成骨架——**目標是使用者讀完就能拍板，不是最短**。

**Gate**：使用者對**確認卡**說「可以」才進 S2（不要求他讀 spec.md）。
**核准前禁止動任何程式碼。**

**完成判準**：spec.md 落檔、確認卡經使用者點頭（seam 屬內部決策，見上；
代答的決策以 Assumptions 標明）。

### 可選支線：prototype（拋棄式原型）

規格階段對「狀態模型合不合理／UI 該長怎樣」拿不準時，先派 sonnet 做拋棄式
原型回答那一個問題：一個指令能跑、不持久化、不寫測試、不抽象化，
問題答完就刪（答案記進 spec）。禁止把原型碼直接搬進正式程式。

## S2 設計（design.md）

照 `templates/design.md` 派 Plan agent（一般 sonnet；跨檔架構或約束互相牽制
達 3 個以上用 opus）。

**設計必含（寫檔／寫狀態的副作用）**：只要這次會新增「寫檔案、寫日誌、寫狀態」
的行為，路徑就要設計成**可注入**——預設值指向正式產物，但呼叫端能替換成暫存路徑。
沒有這個 seam，既有測試會照著預設路徑把假資料寫進正式產物（S3、S5 有對應的驗收，
見下）。

**高風險設計（介面難逆轉、影響超過 3 個模組）→ Design It Twice**：
平行派 2–3 個 agent，各給不同的設計約束（例：「介面最小化」vs.「為最常見
呼叫者優化」vs.「ports & adapters」），再派一個評審 agent 用
深度／locality／seam 位置比較並給出**單一推薦**（可以是混合方案）。

**驗**：派 haiku read-back——「照這份設計能不能直接開工？有無內部矛盾？spec 的
Future-Proofing 每一條，設計裡說得出到時怎麼接嗎？」（`templates/review.md`）。

**read-back 不擋出題（2026-10-22 使用者定案）**：design.md 一落檔就派 read-back；指揮官
同時做 S3 拆解，tasks.md 一切好就派 S4a 出題者，不等 read-back 結果（有設計 gate 時，
出題等使用者點頭才派，read-back 照樣先跑）。read-back 不過，由指揮官直接改 design.md，
不退回設計者重寫第二輪；改到已派出的出題者會用到的地方（介面名稱、測試前提、數字），
同步告訴那幾位出題者。指揮官改完不再派第二次 read-back：出題者照設計寫測試、對空殼
編譯，就是第二道檢查（名稱撞名編不過、某個數字到不了、某個前提不成立，多半由他們抓到）。

**Gate**（完整深度才有的第二道；小份量可把設計摘要併進 S1 確認卡的「打算怎麼做」欄、
或直接省略，由指揮官在份量宣布時說明）：給使用者一張**白話設計摘要**（這個設計打算
怎麼做、最有風險的一兩個決定、會不會改到你在意的行為、以後確定要做的功能到時怎麼接上），
點頭才進 S3；技術細節（seam、模組、要動的檔案）留在 design.md。

**完成判準**：design.md 落檔、read-back 的意見指揮官已處理完（不擋出題）、
有設計 gate 時使用者已核准。

## S3 拆解（design → tasks.md）

指揮官把設計切成 **vertical slice（tracer bullet）**：

- 每片是**貫穿所有整合層的薄縱切片**（schema＋邏輯＋介面＋測試都含），
  不是「先做完整個資料層」的橫切片。
- 每片完成後**可獨立展示或驗證**。
- 發現「先整理結構才好下刀」→ prefactor 片放最前面：
  *make the change easy, then make the easy change*。
- 每片大小以 **sonnet 一次派工能完成**為準；拿不準就切小。
- **design.md「未來功能怎麼接」的每條預留，都要落在某一片的 What to build**，並附至少
  一個看得到的驗收點（例：多出來的欄位存進去讀得回來、舊格式的資料仍讀得到），
  出題者才會替它出測試；沒落到任何一片的預留等於沒做。
- **新增寫檔／寫狀態的副作用時**：把「既有測試全部改為注入暫存路徑」列進同一片
  的驗收（可注入的 seam 由 S2 給，見上；**S2 漏了就在最前面加一片 prefactor 補上**，
  不要在 S3 硬改）。既有測試不會為了新功能而改，但新功能的預設路徑對它們照樣
  生效——測試的假資料會寫進正式產物，之後查真事故時會誤判。
- **逐檔問「這個檔案有沒有排程任務或常駐程序直接執行工作區的版本？」**
  有的話**寫檔＝上線**：新行為必須藏在預設關閉的閘門後（旗標／標記檔），由遷移
  步驟刻意打開，或先暫停該排程再動工。這條約束要寫進派給實作者的 prompt。

**tasks.md 格式**：頂部一行指向 spec.md；然後每片一節：

```
## T1：<標題>
- 狀態：pending | in-progress | done | blocked
- Blocked by：<片編號或無>
- 涵蓋 user stories：<編號>
- What to build：<端到端行為描述，講「系統該做什麼」，不講改哪個檔案>
- 驗收 checklist：<每條可獨立客觀驗證，禁止「運作正常」這種空話>
- Out of scope：<這片不做的>
```

**完成判準**：spec 的每個 user story 至少被一片涵蓋；依賴排好序；
每片的驗收 checklist 逐條可驗。

## S4 實作（逐片：先出題、再實作弄綠）

每片走兩個獨立角色：**同一片的出題者與實作者不得是同一個 subagent**（三角色分立與
小修例外見 §0）。

### S4a 出題（fresh-context opus，先紅）

進實作前，先照 `templates/test-design.md` 派一個**只讀 spec、沒參與實作**的
opus agent，依該片的 What to build 與 spec 設計驗收測試。它**只針對這個功能出題**：
這片的行為、真的可能出錯的邊界與錯誤路徑都要有測試，但不替既有功能補測、不寫重複的
測試（測試越多，之後每次跑越慢）；實際跑到全紅（只跑這批新測試；紅在「未實作」而非
測試自己寫壞），並誠實回報自己覺得還沒覆蓋到的缺口。這套測試是實作的**唯一驗收標準**。

**片數 3 片以上時，出題並行**：開工時（tasks.md 一切好，不等 read-back，見 §S2）把所有片
的出題一起派出去，不要一片出題、一片實作地排隊。測試環境同時只能一個程式開啟時，出題者先把測試寫在暫存區、不開測試環境；輪到
那一片時，由指揮官（或叫回原出題者）把測試放進專案、只跑這批新測試確認紅。後面幾片的
題目是照設計寫的，前提偶爾會錯，跑紅時發現就退回出題者修。

**測試換掉，不要疊上去（2026-10-22 使用者定案）**：出題者發現新測試已完整涵蓋某條既有
測試時，只在回報裡列「建議刪除」，不自己刪。閱卷者逐條確認；確認過的清單寫進交付回報，
請使用者點頭（刪測試等於拿掉一道保護）。點頭後不在本功能刪，記進 `docs/STATUS.md` 待辦，
**下一個功能開工時第一件事刪掉**，由那個功能的全套兜底。

**出題三條硬紀律**（打正式呼叫路徑、外部資源驗「還可用」、替身與被測對象走同一條路徑）
寫在 `templates/test-design.md` 的做法規則；派工照模板貼，不刪這三條。

**展示「紅」的手段限定**：用新測試打尚不存在的介面；要有空殼才編譯得過時，空殼由指揮官
先建。出題者不改產品程式（改壞程式看紅是閱卷者的反證，見 §0）。
**禁止對工作區做整樹操作（stash、checkout 還原）**——多片連續實作期間工作區
長時間未提交，整樹操作會把前面所有片的成果一起藏起來，靠事後還原救回。
指揮官在多片 pipeline 中期可落中繼 commit 降低暴險。

### S4b 實作（general-purpose sonnet，弄綠）

依依賴序逐片照 `templates/tdd-task.md` 派工（sonnet 預設；純機械式套模式可
haiku）。實作者的任務是**把 S4a 出的紅燈弄綠**：不得修改或刪弱那套驗收測試、
不得用 hardcode／mock 內部協作者去騙過測試；為自己開發方便寫的臨時 micro-test
不算驗收標準。核心紀律（測試只打核准 seam、不重構、不加投機功能）寫在模板裡。

指揮官每片收工時做三件事：
1. 核對回報的三段式（做了什麼／驗證輸出／沒做什麼），驗證輸出必須是實跑結果
   （核對測試紀錄即可，不另外重跑，見 §0）；確認實作者是「讓既有驗收測試變綠」，
   不是改題目來遷就實作。
2. 更新 tasks.md 該片狀態。
3. 決定下一片或處理卡點。

**卡住**：照 `10-model-dispatch.md` §5 升降級，禁止讓 subagent 原地重試超過上限。**難 bug** 另有紀律（`41-pipeline-branches.md` §1 診斷支線，見本檔末）。

**完成判準**：tasks.md 全部 done，每片有實跑測試輸出為證。

## S5 驗收（兩軸審查＋重構）

1. **全套測試一次，含慢測試，排在閱卷與所有修改之後**（下面第 2–4 點做完才跑；
   能不能直接引用舊紀錄照 §0「測試怎麼跑」；要跑時輸出大就派 agent 跑、落檔、回結論）。
   - 跑完確認**正式產物（資料目錄、日誌、報表）的檔案大小與 mtime 沒變**——
     測試把東西寫進正式產物是最容易漏掉的一類污染。
   - **在隔離工作區（worktree）開發過的功能**：基底一律取本機 HEAD，開工第一件事
     是對版本確認與主樹一致（工具預設可能從遠端分支開，遠端落後就等於在舊基底上
     寫碼）；且隔離區缺不進版控的真實資料目錄，那裡的綠燈證明不了主樹行為——
     **全套必須在合併後的主樹再跑一次**才算驗收完成。
2. **兩軸審查**：照 `templates/feature-review.md` 派 **fresh-context opus，且
   獨立於 S4a 出題者與 S4b 實作者**（三角色分立的第三角）——
   **Spec 軸**（對照 spec.md＋tasks.md：缺漏、scope creep、假完成）與
   **Standards 軸**（程式異味，判斷題）。兩軸**分開回報、不合併排名**：
   程式可能「規範全過但做錯了東西」，混在一起會互相遮蓋。
   - **派閱卷前先跑機械檢查（2026-10-22 使用者定案）**：空 catch、殘留的除錯輸出、註解掉的程式碼這三種不靠閱卷者用眼睛找，
     指揮官先跑專案的機械檢查腳本（只看這次新增的行），把輸出貼進派工單，閱卷者只判斷
     列出的每一處該不該留。專案還沒有這支腳本就先補一支：讀版本控制的差異，只檢查新增的行，
     每處印一行「檔案:行號 種類 原文」；判斷「註解掉的程式碼」只抓長得像程式的（呼叫或賦值結尾、
     if／for 加括號、單獨的大括號），句尾剛好有分號的說明文字不算，否則誤報太多沒人看。
     檔名有空白或非英文字時也要讀得到（版本控制工具常會加引號或在路徑後補字元）。
   - **閱卷的核心價值是找「測試照不到的東西」**：測試綠燈只代表「被寫出來的
     那幾條測試通過」，不代表做對了。閱卷必須拿 **spec（不是拿測試）** 去對
     程式，額外扛一條職責——**查 S4a 那套測試本身漏了 spec 哪些面向**（有哪些
     可觀察行為沒被任何測試涵蓋）。這是閱卷不能被「跑一次測試」取代的原因。
   - **effort**：日常派工靠 opus＋模板裡「逐條對 spec、主動找漏做與假通過、想清楚再下結論」
     逼出高 effort；走 Workflow 編排時本關設 high／max（見 `10-model-dispatch.md` §0）。
3. **重構在這裡做，但只修必修的**（不在 S4 的 red→green 迴圈裡）：閱卷把每個寫法
   發現標成「必修」或「可延後」。**沒有必修項目時，不開修正＋複查那一輪**——可延後的
   記進 `docs/STATUS.md` 待辦，下次改到那個檔時順手修。有必修的照 `templates/refactor.md`
   派工（會造成錯誤行為的，先另派一個出題者補一條會紅的測試，再交給修的人修），修的時候只跑相關測試；修完照舊派
   複查，範圍只限修的部分，由它做反證，最後再跑交付前那次全套。
4. Spec 軸的缺漏與測試漏洞（有行為沒被任何測試涵蓋、或反證時測試不會紅）→ 一律當場補，
   開新 slice 回 S4。補完怎麼驗照 §0「閱卷後補的東西怎麼驗」。
5. **破壞性程式必做反證（由閱卷者做）**：功能會刪檔、覆寫既有資料、清理舊產物時，把防線
   逐條放寬跑測試，每放寬一條都必須有測試變紅；抓不到的那條就是沒被測到，補到
   抓得到為止（等價變異除外，但要說得出為什麼等價）。跳過這步就會帶著一支
   「測試全綠的誤刪程式」上線。

**完成判準**：`20-judgment.md` §2 的完成 checklist 全部打勾。

## S6 收尾

- 過程中定案的新術語 → 更新根目錄 `CONTEXT.md`（沒有就建，只放詞彙定義，
  **絕不放實作細節**）。難逆轉＋日後會令人驚訝＋真 trade-off 的決策
  （三者全中才寫）→ `docs/adr/NNNN-slug.md`，1–3 句講脈絡與為什麼。
- **下版本號**：本功能出貨 → 照 `50-versioning.md` bump MINOR（fix 模式 bump
  PATCH）；commit 標題與 DEVLOG 首句用同一字串 `vX.Y.Z: <desc>`，
  不疊 T 編號／spec slug／ADR 編號。
- 向使用者**誠實回報**：做了什麼／沒做什麼／假設了什麼，附最終測試輸出。
  有閱卷確認過的「建議刪除的舊測試」時，列出來請使用者點頭（見 §S4a「測試換掉，不要疊上去」）。
- **回報耗時**：附 §0「全程計時」那張表——各階段實際花多久、等使用者多久、
  哪一段最久與原因。查不到就明說沒計時，不要用猜的。
- 踩了坑 → 照 `30-maintenance.md` §3 寫教訓。
- 本功能就是 `docs/ROADMAP.md` 裡的某一條 → 刪掉那一條；只做完一部分 → 改寫成只剩沒做的。只替它做了預留不算做完，那條留著。
- 更新 `docs/STATUS.md` 與 `docs/DEVLOG.md`（格式規則見
  `.claude/skills/wrap/SKILL.md`，那是唯一權威來源）。

## Fix 與功能同流程

修 bug **不再是獨立的簡化流程**——照本檔 S0–S6 跑，深度隨份量縮放（典型的薄 fix 就是
§0 份量表「小修」那一欄；歸因不明的難 bug 進診斷支線，見下）。**S1 確認卡 gate 與 S5
驗收照跑，不因是 fix 而省。**

## 兩條支線（在 `41-pipeline-branches.md`，遇到就必讀）

- **診斷支線**：任何階段碰到歸因不明的難 bug、或卡住想開始猜原因時，先讀 41 檔 §1
  （先建會變紅的緊迴圈才准假設）。
- **試效果模式**：功能已過 S1 確認卡、使用者看了展示後要「換個方式試／這裡調一下」這類
  看效果的調整時，宣布進入前先讀 41 檔 §2。**放寬（不寫新測試、不派閱卷）只限定案前**；
  定案要再過一張三格確認卡，之後照一般流程出題、閱卷、全跑。
