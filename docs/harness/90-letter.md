## 三件重要的事

### 1. 這個專案還不是 git repo——你的第一個實作任務開始前先處理這件事

建制當下沒有版本控制。這代表任何覆寫都是永久的。開始寫產品程式碼之前，
先建議使用者 `git init`（要他同意，因為這改變專案狀態）。在那之前，
`30-maintenance.md` 的備份程序是唯一的安全網，別省。
另外注意專案目錄叫 "Harness Template"——如果使用者日後把這套制度複製到
其他專案，記得提醒他：`10-model-dispatch.md` 第 0 節的環境實況和記憶目錄
路徑是綁定這台機器、這個目錄的，複製過去要重新核對。

### 2. 你有一個制度檔以外的持久記憶系統，兩者分工不同

記憶目錄在 `~/.claude/projects/C--Project-Workspace-Harness-Template/memory/`，
每 session 自動載入其索引 `MEMORY.md`。分工：
- **制度檔（docs/harness/）**：怎麼工作的規則。跟著專案走，使用者看得到、
  可以審。
- **記憶（memory/）**：使用者是誰、他給過什麼回饋、進行中的目標。
  跟著機器走。
把使用者的糾正寫進記憶（type: feedback，附 Why 和 How to apply），把工作
規則的教訓寫進制度檔（`30-maintenance.md` 第 3 節格式）。寫錯邊的後果：
寫進記憶的規則其他協作者看不到；寫進制度檔的個人偏好會污染制度。

### 3. 這個環境是 Windows + PowerShell 5.1，坑很密

弱模型最常在這裡浪費整輪重試：
- PowerShell 5.1 **沒有 `&&`／`||`**，會直接 parser error。用
  `A; if ($?) { B }`，或改用 Bash 工具跑 POSIX 語法。
- `Out-File`/`Set-Content` 預設 **UTF-16 LE**，寫給其他工具讀的檔案要加
  `-Encoding utf8`。但一般檔案操作根本別用 shell——用 Write/Edit 工具。
- 路徑含空格（本專案路徑就有：`C:\Project Workspace\...`），凡是進 shell
  的路徑一律加引號。
- 大量 MCP 工具（Figma/Canva/Notion）是**延遲載入**的：要用之前必須先
  `ToolSearch` 拉 schema，直接呼叫會失敗。
- 有現成 skills 可用：驗證改動用 `/verify`，審 diff 用 `/code-review`。
  別自己土法煉鋼。

## 這套制度最可能的退化方式與預防

1. **儀式化**：照抄模板欄位但不思考內容——驗收條件寫成「功能正常」這種
   空話，三件套形同虛設。預防：`20-judgment.md` 第 5 節的底線是可實測的
   （haiku read-back 答不出下一步就是不合格）；驗收條件寫不出客觀檢查法
   時，回去重讀 `00-design-baseline.md` 失效模式 2。
2. **靜默繞過**：趕時間的 session 覺得「這次很簡單」就跳過派工和驗證，
   一次沒事、兩次沒事，直到出大事，而且沒人記錄。預防：硬規則放在
   CLAUDE.md（每 session 必載入）；如果你發現自己在繞過，至少在回報裡
   寫明「本次未按制度驗證」，讓使用者知情。
3. **規則堆積**：每次踩坑都加規則、從不刪，兩個月後制度檔長到沒有模型
   會真的讀完，等於沒有制度。預防：`30-maintenance.md` 第 4 節的精簡
   觸發線是硬數字（250 行/10 條教訓/80 行），達標就得執行，不是建議。
4. **環境漂移**：型號更名、工具參數改變，第 0 節過時後模型照舊派工，
   派工失敗又被當成模型太弱而錯誤升級。預防：派工報「unknown model」
   類錯誤時，第一反應是核對 `10-model-dispatch.md` 第 0 節是否過時，
   而不是升級重試。

## 這套制度的極限（誠實條款，使用者要求寫明）

拆解、驗證、多樣本評審能把**執行品質**撐到接近建制者水準；但**模糊題與
品味判斷**（API 的長期設計、文案語氣、產品取捨）補不了——rubric 只能告訴
你「這超出可靠範圍了」，不能替你答對。遇到時照 `20-judgment.md` 末節：
升級模型、多答案評審、或對使用者明說做不到並給出你的傾向與理由。
假裝有把握是這套制度裡最貴的錯誤。
