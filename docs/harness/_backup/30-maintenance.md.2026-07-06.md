# 30 — 維護協議：如何安全地更新制度檔

> 讀者：未來任何想修改 `CLAUDE.md` 或 `docs/harness/` 的模型。
> 原則：制度檔是所有 session 的共用基礎設施，改壞的代價由之後每個 session 承擔。

## 1. 權限分級

**可自行修改（改完在回報中告知使用者即可）**：
- `10-model-dispatch.md` 第 0 節「本環境實況」——型號、工具、skill 清單過時就更新。
- 各檔的「建制時的假設」段落——假設被實況推翻時修正。
- `templates/` 新增模板、或在既有模板加欄位。
- 各檔追加「教訓」條目（格式見第 3 節）。

**動之前必須先問使用者**：
- 修改或刪除 `CLAUDE.md` 的硬規則。
- 刪除任何制度檔、或大幅改寫（超過該檔三分之一）。
- 修改 `00-design-baseline.md` 的三大失效模式本身（追加預防手段不用問）。
- 放寬任何上限（重試次數、回報行數、驗證要求）。收緊不用問。

## 2. 備份程序（硬規則，改任何制度檔前執行）

1. 複製原檔到 `docs/harness/_backup/＜原檔名＞.＜YYYY-MM-DD＞.md`
   （目錄不存在就建立；同日多次修改就加 `-2`、`-3` 後綴）。
2. 改完後，用 `20-judgment.md` 第 5 節的文件底線驗法驗收
   （派 fresh-context read-back）。
3. 若修改影響路由或檔名，同步更新 `CLAUDE.md` 的目錄結構與路由表。
4. `_backup/` 超過 10 個檔案時，刪除最舊的、只保留每檔最新 3 份。
   （此清理不受 CLAUDE.md 硬規則 6 限制——`_backup/` 內全是本協議自建的
   副本，屬例行維護；除此之外的刪檔仍要先問。）

## 3. 教訓寫回（每次踩坑後）

**寫到哪**：
- 派工/模型選擇踩的坑 → `10-model-dispatch.md` 末尾「教訓」節。
- 判斷失誤（該問沒問、該停沒停）→ `20-judgment.md` 對應小節追加正/反例。
- 模板欄位不夠用 → 直接改該模板。
- 環境陷阱（工具行為、平台怪癖）→ `CLAUDE.md` 若會出大事，否則
  `10-model-dispatch.md` 第 0 節。

**格式（固定三行，控制膨脹）**：
```
- [YYYY-MM-DD] 坑：＜一句話，發生了什麼＞
  因：＜一句話，為什麼會發生＞
  改：＜一句話，之後怎麼做／已改了哪條規則＞
```

寫教訓不需要備份程序（追加不算修改既有內容），但改既有規則需要。

## 4. 精簡協議（防止制度檔長成沒人讀的長文）

**觸發條件（任一達標就精簡）**：
- 單一制度檔超過 250 行。
- 「教訓」條目超過 10 條。
- CLAUDE.md 超過 80 行。

**精簡方法**：
1. 先備份（第 2 節）。
2. 教訓條目中已經「畢業」的（規則本文已吸收其內容）直接刪除。
3. 重複或互相包含的規則合併，保留較具體的那條。
4. 精簡後 read-back 驗收：問驗收 agent「精簡前後有沒有規則消失或變弱」，
   有就補回。
5. 精簡屬於大幅改寫時（超過三分之一），先問使用者。

## 建制時的假設（日後可依實況修正）

- 假設本專案之後會 `git init`；在那之前 `_backup/` 是唯一的版本保護，
  執行備份程序不可省略。git 化之後備份程序仍保留（git 保護的是 commit 過的，
  備份保護的是工作中的）。
