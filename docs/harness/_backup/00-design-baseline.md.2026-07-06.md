# 00 — 設計基準：弱模型三大失效模式與制度性預防

> 本檔是整套 harness 的設計依據。其他制度檔（10、20、30、templates）的每一條規則
> 都應能追溯到這裡的某個失效模式。改制度前先讀這份，確認你的修改沒有重新打開
> 已經被擋住的洞。
>
> **建制背景**：本檔由 Fable 5 於 2026-07-05 在空白專案上建立，讀者是之後長期
> 運作的較小模型（Sonnet / Opus / Haiku）。「弱模型」在本檔中指相對 Fable 的
> 所有執行模型，包含 Opus。

---

## 失效模式 1：Context 揮霍 — 主對話被原始資料淹死

### 症狀
- 主對話直接 Read 整個大檔、遞迴列目錄、把網頁全文拉進來，只為了找一個答案。
- Subagent 回報時把整份檔案內容貼回主對話。
- 長產物（報告、diff、log）直接印在對話裡而不是落檔。
- 結果：session 中途 context 耗盡，被迫摘要，摘要後遺失關鍵細節，後半段品質崩盤。

### 為什麼弱模型特別容易犯
弱模型傾向「先把東西都看一遍再說」，缺乏「這次讀取值多少 token」的成本直覺；
而且它不會意識到 context 是全 session 共用的預算，一次揮霍會傷害兩小時後的自己。

### 制度性預防（不是事後補救）
1. **指揮官不下場**（→ `10-model-dispatch.md` 第 1 節）：大量讀取、掃檔、查網頁、
   批次改檔一律派 subagent。主對話只進結論。
2. **回報合約**（→ `10-model-dispatch.md` 第 4 節）：subagent 只回結論 +
   `檔案:行號`；超過約 30 行的產物一律落檔，只回傳路徑。
3. **派工模板內建回報格式欄位**（→ `templates/`）：每次派工都被迫寫明「回報上限
   與格式」，弱模型照抄模板就自動守約。
4. **CLAUDE.md 只放路由**：根檔案每 session 都載入，所以只放指路，不放內容，
   避免固定稅。

## 失效模式 2：無驗收開工 — 失焦與範圍蔓延

### 症狀
- 收到模糊需求就直接動手，做到一半發現理解錯了，已改的檔案變成災難現場。
- 做 A 的路上「順手」重構 B、升級 C 的依賴，範圍越滾越大。
- 沒有「完成」的定義，於是永遠在補一點點，或反過來提早宣布完成。

### 為什麼弱模型特別容易犯
弱模型對「這個需求有幾種合理解讀」不敏感，會鎖定第一個看起來合理的解讀衝到底；
而且它把「有在產出東西」當成「有在推進任務」。

### 制度性預防
1. **派工三件套強制化**（→ `10-model-dispatch.md` 第 2 節）：任何委派必須含
   目標與動機、驗收條件、回報格式。模板（→ `templates/`）把三件套做成填空，
   沒填完就不派。
2. **完成的定義外化**（→ `20-judgment.md` 第 2 節）：「何時算真的完成」是一份
   checklist，不是感覺。
3. **停下來問的判準**（→ `20-judgment.md` 第 3 節）：明列哪些情況必須先問使用者
   而不是自己猜，並附正反例，避免弱模型把「猜」當「自主」。
4. **範圍鎖**：模板的驗收條件欄位要求列出「不做什麼」，順手改的衝動在派工當下
   就被文字擋住。

## 失效模式 3：自信錯誤 — 自己驗自己、錯了就原地重試

### 症狀
- 宣稱「已完成並測試通過」但其實沒跑過任何驗證，或只跑了自己寫的、必過的驗證。
- 同一個錯誤用同一招重試三、四次，每次只改一點點，燒掉大量時間與 token。
- 寫檔後不確認落地、改設定後不確認生效。

### 為什麼弱模型特別容易犯
產生答案的路徑和檢查答案的路徑在同一個 context 裡，會共享同一個盲點；
弱模型又特別不願意承認「我卡住了」，因為重試看起來像在努力。

### 制度性預防
1. **驗證不自驗**（→ `10-model-dispatch.md` 第 6 節）：驗收派 fresh-context
   subagent。檔案用 read-back、程式碼用測試或實跑、高風險判斷加第二意見。
2. **重試上限硬編碼**（→ `10-model-dispatch.md` 第 5 節）：同一子任務最多重試
   兩輪，之後強制升級模型或換路，附完整失敗軌跡。
3. **方向錯誤訊號清單**（→ `20-judgment.md` 第 4 節）：明列「該換路而非重試」
   的訊號，讓弱模型有客觀依據打斷自己的重試迴圈。
4. **誠實回報是硬規則**（→ `CLAUDE.md` 硬規則）：測試失敗就說失敗並附輸出；
   沒做的步驟就說沒做。違反這條的成本寫在最高層級檔案裡。

## 建制時的假設（日後可依實況修正）

- 假設未來任務型態以軟體開發為主（搜尋、實作、重構、研究、審查五類，
  見 `templates/`）。若專案方向不同，先改模板再改守則。
- 假設可用 subagent 模型為 `haiku` / `sonnet` / `opus` / `fable` 四種
  （2026-07-05 實測 Agent 工具的 model 參數）。型號變動時更新
  `10-model-dispatch.md`。
- 假設主要執行模型是 Sonnet 等級。所有規則都以「Sonnet 跑得動」為底線設計，
  不依賴 Fable 級能力。（2026-07-05 使用者自述主對話多為 Opus——向上相容，
  底線不變。）
- 2026-07-05 新增 `40-pipeline.md` 與 design／tdd-task／feature-review 三個
  模板，方法論萃取自 mattpocock/skills（見 `docs/notes/mattpocock-skills-extract.md`）。
  pipeline 的每個階段規則同樣追溯到本檔三大失效模式：S1 規格 gate 與範圍鎖
  對應失效模式 2；S4 先紅後綠與 S5 fresh-context 兩軸審查對應失效模式 3；
  逐片派工與產物落檔對應失效模式 1。
