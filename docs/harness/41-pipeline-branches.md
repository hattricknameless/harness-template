# 41 — Pipeline 支線：難 bug 診斷、定案前試效果

> 讀者：主對話模型（指揮官），以及卡在難 bug 的實作者。本檔是 `40-pipeline.md`
> 的延伸，只放少數情況才用的兩段；遇到下面情況**必須先讀對應一節**再動手：
> - **歸因不明的難 bug**（任何階段、任何角色）→ §1 診斷支線。
> - **使用者看了展示後要求換個方式試、調效果**，準備宣布進試效果模式 → §2。
> 本檔沒寫到的，一律照 `40-pipeline.md`；衝突時以 `10-model-dispatch.md` 與
> `20-judgment.md` 為準。

## 1. 診斷支線（難 bug 時進入，適用任何階段）

核心：**先建立會變紅的緊迴圈，才准開始假設。**

1. **建迴圈**：一個能命中該 bug 確切症狀、秒級、確定性、agent 可無人值守
   執行的指令（failing test → 腳本 → bisect harness，由簡入繁）。
   在這裡花不成比例的力氣；沒有迴圈就去讀碼建理論是本支線要禁止的行為。
   真的建不出來 → 停下，向使用者要重現環境／捕獲產物（log、trace）。
2. **重現＋最小化**：確認紅的是使用者描述的那個症狀；一次剪一個元素，
   剪到「拿掉任一個就變綠」。
3. **假設**：先列 3–5 個排序過的可證偽假設（「若 X 是原因，改 Y 應使 bug
   消失」），才准動手驗證；講不出預測的假設丟掉。
4. **插樁**：一次改一個變數；debugger 優於針對性 log；禁止「全部 log 再
   grep」；每條 debug log 加唯一前綴（如 `[DEBUG-a4f2]`）供清理。
   效能問題：先建 baseline 量測再二分，不靠 log。
5. **修復＋回歸測試**：修復前先在正確的 seam 寫回歸測試（看它紅→修→看它綠）；
   沒有正確 seam 就記錄這個事實，不硬寫假信心測試。
6. **清理**：grep 前綴清光插樁；重跑第 1 步的原始迴圈確認不再重現；
   把證實為真的假設寫進 commit 訊息。

重試上限照舊：禁止讓 subagent 原地重試超過 `10-model-dispatch.md` §5 的上限。

## 2. 試效果模式（定案前的快速迭代）

> 2026-09-23 使用者核准。本模式**只在定案前**放寬出題與閱卷，定案後照常全跑。

**什麼時候進**：功能已經有使用者能直接打開來看的入口（展示畫面、場景、頁面），而使用者的
回應是「換個方式試試／這裡調一下／看起來不對」這類**看效果**的要求，不是新功能。指揮官
一句話宣布「進試效果模式」；使用者可否決。新功能、新規則、碰資料／資金／live、刪檔、
改場景結構，都不適用，照一般份量分級走。

**怎麼進（S1 不省）**：只能開在**已經過 S1 確認卡**的功能上，試的是那張卡範圍內的做法；
超出卡的範圍（新行為、新規則）就是新需求，照一般流程重跑 S1。

**怎麼做**：
- 指揮官自己改，或派**一個** sonnet 改完就回來。不改 spec／design，只在該功能的 spec 目錄
  `trials.md` 追加一行：時刻｜試了什麼｜使用者怎麼說。
- 能做成設定值的就做成設定值；一次可做 2–3 個相近變化，讓使用者用按鍵或開關切換，
  一輪比較多個選項。
- 驗證只做：能編譯、沒有錯誤訊息、受影響的既有測試通過。**不寫新測試、不派閱卷**。
  既有測試因行為刻意改變而變紅時，不要硬修測試，記進 trials.md，定案時一起處理。
- 回報用「可以看了」＋怎麼看（操作／預期表格）＋這輪改了什麼。**不說完成、不提交、
  不下版本號。**
- 計時照記（timing.md 標「試效果」）。

**怎麼出**：使用者說定案（「就這樣／可以了」）→ 給一張**三格確認卡**（最終行為／跟原本
那張卡差在哪／完成長怎樣），點頭才算定案（這就是本輪的 S1 gate，不省）→ 回到一般流程：
把 trials.md 的最終狀態整理進 spec／design → S4a 為**最終行為**出題（程式已經在了，題目寫完可能直接綠；由閱卷者逐條反證這些測試會不會紅）→ S4b 補齊 → S5 獨立審查照舊 → 使用者實測 → S6。放寬的只有「定案前不出題、
不閱卷」這一件；`CLAUDE.md` 的不自驗與誠實回報全程照舊。試到最後不要的做法，定案前
還原乾淨，不留在程式裡。
