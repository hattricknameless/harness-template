# 派工模板：實作單片，把驗收測試弄綠（pipeline S4b）

> 用途：實作 tasks.md 裡的一個 vertical slice。一次派一片。
> 建議派法：subagent_type=`general-purpose`，model=`sonnet`；
> 純機械式照模式套用可 `haiku`。
> **三角色分立：本模板是「實作者」，驗收測試由 S4a 出題者（另一 agent）先出好、
> 已是紅的；你的任務是弄綠，不是出題。** 例外——小修份量若指揮官把出題併入本步，
> 才由你自己先紅後綠（見下方「若本片未附驗收測試」）。

```
【目標與動機】
實作以下 slice（出自 ＜docs/specs/<slug>/tasks.md＞ 的 T＜n＞），把已附的驗收
測試從紅弄綠：
＜貼入該片全文：What to build ／ 驗收 checklist ／ Out of scope＞
設計依據：＜docs/specs/<slug>/design.md＞，其中本片相關的模組與 seam：＜摘要＞
驗收測試（S4a 出題者所出，目前全紅）：＜測試檔路徑；跑法＞

【做法規則（違反即重做）】
- 目標是讓那套驗收測試變綠，且不弄壞既有測試。
- **不得改題**：禁止修改、刪除或弱化那套驗收測試；禁止用 hardcode 回傳值、
  mock 內部協作者、skip 測試等手段去「騙過」它。判斷法：若你的改法讓測試綠了
  但真實行為沒做對，就是騙題，重做。
- 為自己開發方便可寫臨時 micro-test，但那不是驗收標準、收工前自行清理。
- 測試只打核准的 seam：不測 private、不 mock 模組內部的協作者。
  判斷法：實作全部重寫而行為不變時，測試不應該壞。
- mock 只准打在系統邊界：外部 API、資料庫、時間、亂數。
- 一次一片：不重構既有碼、不加「以後可能用到」的功能、不預寫未來測試。
  例外：design.md「未來功能怎麼接」列的預留（介面、資料欄位、擴充位置）照做，
  那是核准過的設計，不算投機；它沒列的一律不加。
- **若本片未附驗收測試（小修併步模式）**：先紅後綠——先在指定 seam 上寫會失敗的
  測試、實際跑到紅、附輸出；期望值取自獨立來源（spec 例子、手算、已知字面量），
  禁止用與實作相同的算法反推期望值；再寫剛好讓它通過的實作，附綠的輸出。
- 卡在難 bug：先建一個秒級、確定性、能變紅的重現指令，才准開始猜原因
  （完整紀律見 40-pipeline.md 診斷支線）。同一做法最多兩輪，之後停手回報。

【驗收條件】
- 驗收 checklist 逐條過，每條附證據。
- 本片測試全綠，且這次改到的模組的既有測試也綠（跑 ＜相關測試指令＞ 確認；改數值或
  資料檔時，用舊數值與資料檔路徑搜得到的測試也算）。
  **不跑全套**——全套由指揮官在閱卷與所有修改之後、交付前統一跑一次（見 40-pipeline §0）；也不必故意改壞程式做反證，
  那是閱卷者的事。
- 範圍鎖：Out of scope 的東西一行都不碰。

【回報格式】
三段式，全文 ≤30 行：
1. 做了什麼：改動檔案（路徑:行號）＋ 每個一句話。
2. 驗證：紅→綠的實跑輸出結論（失敗貼原文）＋ 相關測試結果。
3. 沒做什麼／假設了什麼／卡在哪。
- 用詞：只用日常常見的詞，不自創名詞或標籤；術語第一次出現用一句話解釋；
  同一概念全文用同一種說法（完整規則見 CLAUDE.md 溝通方式第 4 條）。
```
