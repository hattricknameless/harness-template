# 派工模板：TDD 實作單片（pipeline S4）

> 用途：實作 tasks.md 裡的一個 vertical slice。一次派一片。
> 建議派法：subagent_type=`general-purpose`，model=`sonnet`；
> 純機械式照模式套用可 `haiku`。

```
【目標與動機】
實作以下 slice（出自 ＜docs/specs/<slug>/tasks.md＞ 的 T＜n＞）：
＜貼入該片全文：What to build ／ 驗收 checklist ／ Out of scope＞
設計依據：＜docs/specs/<slug>/design.md＞，其中本片相關的模組與 seam：＜摘要＞

【做法規則（TDD 紀律，違反即重做）】
- 先紅後綠：先在指定 seam 上寫一個會失敗的測試，實際跑它、確認它紅、
  回報中附紅的輸出；再寫剛好讓它通過的實作，附綠的輸出。
- 測試只打核准的 seam：不測 private、不 mock 模組內部的協作者。
  判斷法：實作全部重寫而行為不變時，測試不應該壞。
- 期望值來自獨立來源（spec 的例子、手算、已知字面量）。禁止用與實作
  相同的算法算期望值——那種測試永遠不會不一致。
- mock 只准打在系統邊界：外部 API、資料庫、時間、亂數。
- 一次一片：不重構既有碼、不加「以後可能用到」的功能、不預寫未來測試。
- 卡在難 bug：先建一個秒級、確定性、能變紅的重現指令，才准開始猜原因
  （完整紀律見 40-pipeline.md 診斷支線）。同一做法最多兩輪，之後停手回報。

【驗收條件】
- 驗收 checklist 逐條過，每條附證據。
- 本片測試全綠，且沒有弄壞既有測試（跑 ＜全量測試指令＞ 確認）。
- 範圍鎖：Out of scope 的東西一行都不碰。

【回報格式】
三段式，全文 ≤30 行：
1. 做了什麼：改動檔案（路徑:行號）＋ 每個一句話。
2. 驗證：紅→綠的實跑輸出結論（失敗貼原文）＋ 全量測試結果。
3. 沒做什麼／假設了什麼／卡在哪。
```
