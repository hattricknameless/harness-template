# 派工模板：設計（pipeline S2）

> 用途：把核准的 spec 變成可開工的設計。
> 建議派法：subagent_type=`Plan`，model=`sonnet`（一般）／`opus`（跨檔架構、
> 約束互相牽制 ≥3 個）。高風險設計改用 Design It Twice（見 `40-pipeline.md` §S2）。

```
【目標與動機】
為 ＜spec 路徑＞ 設計實作方案。這份設計會被切成多個 vertical slice 交給
sonnet 級 agent 逐片實作，所以必須具體到「照著做不需要再做設計決策」。

【現況與素材】
- spec：＜docs/specs/<slug>/spec.md＞（seam 清單已經使用者核准，不得擅改）
- 摸底結論：＜S0 找到的相關模組、既有慣例；綠地就寫「綠地」＞
- 詞彙與決策：＜CONTEXT.md 與 docs/adr/ 路徑，存在的話；用詞照 glossary＞

【設計要求】
- 深模組：小介面藏大量行為。介面=呼叫者必須知道的一切（型別＋不變量＋
  錯誤模式），不只是簽名。刪除測試法自檢：想像刪掉這個模組，複雜度若只是
  轉移到 N 個呼叫者身上，它才有存在價值；若複雜度直接消失，它是多餘的轉手層。
- seam 即測試面：測試與呼叫者走同一個介面。想測「介面之後」= 模組形狀不對。
- 可測試性三招：接受依賴而非自己創建；回傳結果而非產生副作用；介面越小越好。
- 外部依賴（第三方 API、DB）：定義 port，production 用真 adapter、
  測試用記憶體內 adapter。只有一個 adapter 的 seam 不要引入。

【驗收條件】
design.md 必須含：
- 模組清單：每個模組的介面（含錯誤模式）與它藏起來的行為。
- seam 位置與每個 seam 的測試策略（用什麼替身、mock 什麼邊界）。
- 資料流：一個主要 user story 從輸入到輸出經過哪些模組。
- 要動／要建的檔案清單（設計即刻會被實作，路徑可以寫）。
- 不做什麼：spec 的 Out of Scope 照抄＋設計層面新增的排除項。
- 品質門檻：haiku read-back「照這份能不能直接開工」答得出來。

【回報格式】
寫到 docs/specs/＜slug＞/design.md。回報 ≤10 行：路徑＋模組數／seam 數＋
你認為最可能出問題的一個設計決策與理由。
- 用詞：只用日常常見的詞，不自創名詞或標籤；術語第一次出現用一句話解釋；
  同一概念全文用同一種說法（完整規則見 CLAUDE.md 溝通方式第 4 條）。
```
