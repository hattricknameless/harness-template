# 派工模板：審查／驗收

> 用途：驗收別的 agent 的產物（read-back、程式碼審查、第二意見）。
> 建議派法：subagent_type=`general-purpose`，model 至少與產出者同級。
> **鐵則：這是 fresh-context 派工——prompt 只給產物路徑與驗收條件，
> 不給產生過程的推理、草稿、或「我覺得應該沒問題」之類的暗示。**

```
【目標與動機】
審查對象：＜產物路徑；程式碼另附「跑什麼指令可驗證」＞
你是獨立驗收者，之前沒有任何人看過這份產物是否合格。你的價值在於找出問題，
找不出問題但其實有問題，是驗收失敗。

【驗收條件（逐條檢查並逐條回答過／不過）】
- ＜條件 1，照原派工單的驗收條件抄過來＞
- ＜條件 2＞
- 通用檢查：內部矛盾？指到不存在的路徑或符號？一個沒有前後文的讀者
  能照著做嗎？

【回報格式】
- 逐條：`條件 → 過/不過 → 證據（檔案:行號 或 指令輸出）`。
- 不過的項目：具體指出錯在哪，不寫改法（改是原作者的事）。
- 最後一行總判定：PASS / FAIL / PASS-with-notes。
- 全文不超過 30 行。
- 用詞：只用日常常見的詞，不自創名詞或標籤；術語第一次出現用一句話解釋；
  同一概念全文用同一種說法（完整規則見 CLAUDE.md 溝通方式第 7 條）。
```
