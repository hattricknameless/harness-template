# Architecture：找出值得整理的模組結構

定期保養用，不是 pipeline 的一站。找出**淺模組**（介面幾乎跟裡面的實作一樣複雜，
呼叫者得懂一堆細節才用得動），提出**加深**方案（把複雜度收進一個小介面後面）。
目標：好測（測試打在同一個介面上）、好找（改一件事只要動一個地方）、AI 好導航。
（方法論 = mattpocock 的 improve-codebase-architecture，2026-08-19 版；
報告改成 Markdown 落檔、加了反方查核，理由見各步。）

**整個流程不改任何程式碼**。會寫的檔只有：報告與掃描／查核回報（都在
`docs/notes/`）、`CONTEXT.md` 詞條、ADR、`docs/STATUS.md` 待辦。真的動手整理，是之後另開一件工作走 `40-pipeline.md`。

## 判斷用的詞彙（對 agent 講時照用；報告與對話裡一律用右欄白話）

| 專業詞 | 對使用者講 |
|---|---|
| 淺模組 | 包了等於沒包的模組：用的人還是得懂裡面一堆細節 |
| 深模組／加深 | 把複雜的東西收進一個簡單的入口後面 |
| 介面 | 別的程式用它時需要知道的東西 |
| seam | 可以從外面接上測試、或換掉零件的那個接口 |
| port／adapter | 先講好的接口／接在接口上的實際零件（正式一套、測試一套） |
| 刪除測試法 | 假設把它刪掉，看麻煩會變少還是只是搬到別處 |
| mock | 測試時拿來代替真東西的假零件 |

沿用 `docs/harness/templates/design.md`「設計要求」那段：深模組、介面＝呼叫者必須
知道的一切、刪除測試法、seam 即測試面、只有一個 adapter 的 seam 不要引入。另加：

- **刪除測試法是唯一入場門檻**：想像刪掉這個模組——複雜度會「集中」到一個更小的
  介面後面嗎？是 → 候選；只是「搬家」到 N 個呼叫者身上 → 它本來就有存在價值，
  不列；直接消失 → 它是多餘的轉手層，可列為「合併掉」的候選。
- **淺的三種長相**：(1) 為了好測而抽出的純函式，但 bug 其實出在呼叫者怎麼用它
  （改一件事要動好幾處）；(2) 模組之間互相洩漏細節、跨過 seam 綁在一起；
  (3) 想懂一個概念得在五個小檔之間跳來跳去。
- **依賴分兩類，決定加深後怎麼測**（與 `templates/design.md` 一致）：同一程序內的
  計算 → 直接合併、測介面；外部依賴（資料庫、自己的遠端服務、第三方 API）→
  定義 port，正式用真 adapter、測試用記憶體內 adapter（mock 只打系統邊界）。
- **測試是替換、不是疊加**：加深後要列出哪些舊的零碎測試變多餘；怎麼刪照
  `40-pipeline.md`「測試換掉，不要疊上去」那條走（列建議→閱卷確認→使用者點頭）。

## 步驟

1. **先定範圍再掃**（只整理會再被改到的地方，沒人碰的程式整理了也回不了本）：
   - 使用者給了方向 → 照方向，跳過下面的推斷。**最有效的用法**是指著下一個要做的
     功能 spec 問「怎麼讓這次改動變簡單」。
   - 沒給方向 → 看 `git log --oneline` 往回一大段，找反覆被改的檔案和區域；
     再看 `docs/STATUS.md` 待辦裡 S5 閱卷留下的「可延後」寫法問題——那是現成的
     摩擦點紀錄（STATUS 不存在或沒有這類待辦就只看 git log）。找不到被改過
     三次以上的區域、也沒有相關待辦時，才放寬到整個產品程式碼。
   - 專案還沒有產品程式碼 → 直接回報「沒有可掃的程式」，結束。
2. **讀既有定案**：根目錄 `CONTEXT.md`（詞彙）與 `docs/adr/`（已定案的決策）存在
   就先讀。報告用專案自己的詞稱呼模組（「訂單收件模組」，不是「FooBarHandler」）；
   ADR 已否決過的方向不重提，除非摩擦大到值得重開——那就在卡片上明寫
   「跟 ADR-NNNN 衝突，但值得重開，因為…」。
3. **派掃描**：照 `templates/search.md` 派 `Explore`（sonnet），範圍＝第 1 步的熱點。
   不給死板的檢查清單，讓它順著讀，記下哪裡讀起來卡：上面「淺的三種長相」、
   哪些地方沒測試或用現在的介面很難測。每個摩擦點要附 `檔案:行號` 與一句證據；
   回報超過 30 行時由指揮官落檔到 `docs/notes/`（Explore 不能寫檔）。
4. **整理候選**：指揮官對每個摩擦點套刪除測試法，過了才成為候選，沒過的直接丟掉。
   候選再標強度（三級都必須先過刪除測試法）——**強烈建議**（刪除測試明確通過、摩擦有檔案證據）／**值得研究**
   （通過了，但划不划算要看程式接下來往哪走）／**純推測**（勉強通過、證據薄，
   只是列出來完整）。
5. **反方查核（不自驗）**：派一個 fresh-context `general-purpose`（opus），
   只給每條候選的摩擦描述與涉及的檔案，不給強度、不給刪除測試的結論、不給第 4 步
   的推理，免得它順著結論點頭。派工 prompt 寫明三條，逐條候選回答「成立／不成立
   ＋檔案證據」：(a) 描述的摩擦在檔案裡真的存在；(b) 刪掉這個模組，複雜度會集中
   到更小的介面後面，而不是搬到呼叫者身上；(c) 加深後確實有測試變簡單或檔案可刪。
   回報落檔 `docs/notes/`，對話只回摘要。指揮官依結果決定：不成立的刪掉、證據
   偏弱的降級。只跑這一輪，不來回複查。
   （原版的已知毛病是幾乎從不說「程式沒問題」；這步就是用來擋這個的。）
6. **寫報告**：落檔 `docs/notes/architecture-review-<YYYYMMDD-HHMM>.md`
   （`docs/notes/` 不進版控，報告不會進 repo）。報告是給使用者讀的，全文照
   `CLAUDE.md` 溝通方式第 1–5 條寫白話，專業詞照上方對照表換掉。格式見下方
   「報告格式」。
7. **停下來問**：對話裡只給報告路徑、候選一覽表（標題／強度／一句話好處）、
   首推哪個與理由，然後問「要深入哪一個？」（附選項與建議答案）。
   **這一步還不提新介面長什麼樣**。
   - 全部候選都是「純推測」（或查核後一條不剩）→ 直說「這次沒找到值得整理的
     地方」，不問、不寫待辦，流程結束。
   - 使用者說了「只要報告」→ 不問，把每個候選各寫一條進 `docs/STATUS.md` 待辦
     （附報告路徑；STATUS 沒有「## 待辦」段就新增），流程結束。
8. **逼問挑中的那一個**：照
   `.claude/skills/grill/SKILL.md` 的訪談與落檔規則，範圍鎖在這個候選上：
   有哪些限制、什麼要收進介面後面、加深後的介面長相、哪些舊測試建議刪（只列建議）、哪些留下。
   想比較幾種介面 → 用 `40-pipeline.md` §S2 的 Design It Twice。過程中：
   - 新模組用到 `CONTEXT.md` 沒有的概念 → 當場補詞條；模糊的詞 → 當場改精確。
   - 使用者以**長期成立**的理由否決候選 → 提議寫 ADR：「要不要記成 ADR，
     以後掃描就不會再提這個？」一時的理由（「現在不划算」）或不言自明的理由不提議。
9. **交棒**：逼問的產出是一個決定，不是程式改動。共識達成後，把它當一件工作照
   `40-pipeline.md` 走（份量照該檔分級；S1 的逼問可以直接用這次共識不重問，
   但確認卡照樣要給使用者核准）。
   **一個 session 只做一個候選**；其餘候選各寫一條進 `docs/STATUS.md` 待辦
   （附報告路徑；沒有「## 待辦」段就新增），之後各自開工。

## 報告格式

- **開頭**：專案名、日期、掃描範圍與為什麼選這個範圍（一兩句）、圖例。不寫前言。
- **每個候選一節**：
  - 標題：說出要做的整理（例：「把訂單收件流程合成一個模組」）
  - 強度＋加深後怎麼測（依賴兩類中的哪一類，用白話寫）
  - 涉及的檔案（清單）
  - 改前／改後對照圖：兩張 mermaid 圖，改前畫出呼叫在小模組間跳來跳去或洩漏的
    地方，改後畫出收進一個模組後的樣子。圖要一眼看懂；看不懂就重畫，不要靠
    文字補救。
  - 現在哪裡卡（一句）／怎麼改（一句）
  - 改完的好處：講具體的——哪些測試變簡單、哪些小檔可以刪、改某件事從動 N 處
    變成動 1 處。不寫「比較乾淨」「比較好維護」這種空話。
  - 跟 ADR 衝突時：一行警示。
- **結尾「首推」**：先做哪一個、一句理由、指回該節。
