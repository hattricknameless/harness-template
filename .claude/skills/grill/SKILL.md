# Grill：逼問到共識，邊問邊落檔

對一個計畫／需求／設計做壓力測試，直到雙方達成共識；過程中把定案的術語與
決策**即時**寫進文件，不要累積到最後一次寫。
（方法論 = mattpocock 的 grill-with-docs：grilling ＋ domain-modeling。）

## 訪談規則（grilling）

1. **一次只問一個問題**，等回答才問下一個。一次拋一串會讓人無所適從。
2. **每個問題必附你的建議答案**，讓使用者可以只回「就照你說的」。
3. 能靠讀碼或讀現有文件回答的，自己查，不准問使用者。
4. 順著依賴序走過每個決策點：先問會影響後面問題的。
5. 用具體情境與邊界案例逼精確：「如果 X 的同時發生 Y 呢？」——
   使用者說「等等，這不該發生」的瞬間就是計畫裡的洞，這是本 skill 的重點。
6. 使用者確認共識前，**禁止動手實作**。

## 落檔規則（domain-modeling）

- 術語一旦定案，立即更新根目錄 `CONTEXT.md`（懶建檔：第一個術語定案才建檔）。
  詞條格式：**術語** ＋ 一兩句定義（定義「是什麼」而非「做什麼」）＋
  `_Avoid_: 要避免的同義詞`。多詞同義時要有主見地選一個，其餘放 Avoid。
- `CONTEXT.md` 只放詞彙定義，**絕不放實作細節**；只收本專案特有的詞
  （timeout、error 這類通用概念不算）。
- 使用者用詞與 glossary 衝突時當場指出；用了模糊／多義詞時提出精確替代。
- 決策**同時滿足三條**才寫 ADR（`docs/adr/NNNN-slug.md`，1–3 句：
  脈絡＋決定了什麼＋為什麼）：(1) 難以逆轉；(2) 沒有脈絡會令人驚訝
  「為什麼這樣做」；(3) 是真 trade-off 的結果（存在真的替代方案）。
  缺一條就跳過——不要堆 ADR。

## 完成判準

- 使用者明說共識達成。
- 定案的術語都已進 `CONTEXT.md`，夠格的決策都已有 ADR。
- 結尾回報：共識摘要（≤10 行）＋ 新增／修改的檔案清單 ＋ 建議下一步
  （若共識是一個可開發的功能，建議 `/pipeline`——S1 可直接把共識轉成 spec，
  不必重問一遍）。
