# /calibrate 派工模板（每個專案一個 sonnet subagent）

> 照填。`＜＞` 為填空欄位。此模板已於 2026-07-06 實跑驗證過
>（61 sessions／92MB，方法論陷阱都踩過並寫在下面）。

```
【目標與動機】
研究使用者過往與 Claude 的互動紀錄，萃取「這位使用者最適合怎樣的協作方式」。
目的是校準工作制度，需要真實工作模式而不是猜測。
分析對象：＜專案目錄絕對路徑＞ 下的 ＜N＞ 個 .jsonl（共約 ＜M＞ MB）。

【素材與做法】
- .jsonl 一行一筆記錄。要的是**使用者親手打的訊息**，機械判準：
  type 為 user，且 message.content 是 **JSON 字串**（人打的 content 直接
  是字串；自動產生的 content 是物件陣列——tool_result 的陣列元素含
  `"tool_use_id"` 欄位，看到就濾掉）。
- 過了上述判準後再濾文字內容：含 <command-name>／<local-command-stdout>
  （斜線指令輸出）、<task-notification>、<system-reminder> 的都不是人打的。
  compaction 自動摘要的標記：記錄含 `"isCompactSummary":true`，或內文以
  "This session is being continued" 開頭。
- 以上都判不定的（例如無標籤的注入內容）：**剔除並在報告中註記剔除數量**，
  不准靠口吻猜測收錄。
- 禁止整檔 Read。用 rg／PowerShell 把候選行抽到 scratchpad 檔再處理；
  優先看最新 session，舊的抽樣。
- 可抽樣少量 assistant 訊息，但只為理解使用者下一句糾正的脈絡。

【要回答的問題】
1. 下指令風格：模糊高層目標還是具體步驟？一次一件事還是一串？訊息多長？
2. 糾正與不滿：糾正 Claude 什麼？（引用原句——這是最重要的產出）
   有無重複出現的抱怨模式？
3. 自主權：偏好先問再做還是做完再報？對擅自決定的反應？
4. 品質重點：驗收時在意什麼？
5. 語言與互動偏好：中英混用、要不要解釋、耐心程度。
6. 反覆出現的工作類型與痛點。

【驗收條件】
- 每個結論附至少一句使用者原話（可截斷，標明來源檔名前 8 碼）。
- 區分「多次出現的模式」與「孤例」，孤例要標明。
- 找不到證據就明說找不到，禁止腦補。
- 範圍鎖：不分析專案商業內容細節；引用含 API key／密碼／個資一律遮蔽。

【回報格式】
完整分析寫到 docs/notes/user-patterns-＜專案代稱＞.md（按 6 題分節，
開頭註明分析日期與訊息樣本數）。對話回報 ≤20 行：檔案路徑＋每題一行
結論＋你認為最重要的三條使用者原話。
```
